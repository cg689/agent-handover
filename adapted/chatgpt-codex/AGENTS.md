# Agent 项目交接技能

本技能指导你完成 AI 编程助手（Agent）项目交接的全流程。

## 核心原则
1. **项目不属于任何 agent**，项目属于它的存储位置。换 agent = 换工人，不是搬项目。
2. **只有写进文件的知识能带走**。会话记忆、长期记忆、项目索引缓存——换 agent 全部丢失。
3. **交接 = 隐性知识显性化 + 验证新 agent 没接错 + 生命周期归档闭环。**

## ⚡ 第 0 步：判断你的角色和场景（必做）

### A. 判断你是旧 agent 还是新 agent
按以下逻辑判断：
1. **优先按用户指令意图**：含"发起交接/换到新 agent/写交接文档"为**旧 agent（交出方）**；含"刚切换过来/刚接手/阅读交接文档入职"为**新 agent（接收方）**。
2. **若指令模糊**：
   - 根目录无 `HANDOVER.md` → **旧 agent（交出方）**。
   - 存在 `HANDOVER.md` 且状态为 `PENDING`（最近提交） → **新 agent（接收方）**。
   - 存在 `HANDOVER.md` 但状态为 `COMPLETED` 或其后已有多次业务提交 → 上次交接已结束，当前为**旧 agent（交出方）**。
3. **存疑时主动向用户确认**："检测到项目中存在历史交接文档。请问您本次是想发起新的交接，还是刚接手该项目？"

### B. 判断完整版还是轻量版（仅旧 agent）
主动问用户："你是要**长期切换**到新 Agent（我之后会停用），还是**临时试用**一下新 Agent（我继续保留）？"
- 长期切换 → 完整流程
- 临时试用 → 轻量版（若放弃试用需删除根目录 `HANDOVER.md`）
- 没说清楚 → 默认完整流程

## 🔀 旧 agent 工作流（交出方）

### 轻量版（临时试用）
1. 确认 Git 状态（无未忽略临时垃圾），提交改动到 git
2. 写精漫版 HANDOVER.md（包含顶部元信息：`交接状态: PENDING`）
3. 告诉用户："请在新 agent 中打开这个项目文件夹，然后说：'我刚从其他 Agent 切换过来，请阅读 HANDOVER.md 完成入职验证。'若放弃试用请删除根目录 `HANDOVER.md`。"

### 完整版（长期切换）

#### 第 1 步：收尾
1. 确认当前分支及 stash 列表，检查 `git status` 确保无未忽略垃圾后提交改动（半成品标注"进行中"）。
2. 打带时间戳的回滚 tag：`git tag handover-before-$(date +%Y%m%d%H%M)`（或 `git tag handover-before-YYYYMMDD-HHMM`）。
3. 运行测试/构建，记录结果。
4. 有远程仓库则推送（含 tag）。

#### 第 2 步：显性化（最易遗漏）
> ⚠️ 必须先完成第 1 步再写文档。若已有旧 `HANDOVER.md`，先备份至 `docs/handover/`，绝不可直接覆盖。

生成两份文档：

**① HANDOVER.md**（快照）包含顶部状态头：
```markdown
---
交接状态: PENDING
交接时间: YYYY-MM-DD
交出方: [当前 Agent 名称]
接收方: [目标 Agent 名称 / 待定]
---
```
内容包括：项目简介和阶段、技术栈、目录结构说明、已完成功能、进行中工作（含优先级）、已知问题与技术债、踩过的坑、设计决策及原因、安全红线、常用命令、工具链与本地数据库/缓存配置。禁止写入明文密钥、Token、私网 IP 或真实业务测试数据。

**② 项目说明书**（长效，如 `AGENTS.md`）包含：项目简介、安全红线、目录结构、依赖与环境、工具链配置、常用命令、测试约定、提交与分支约定、工作约定。

完成后告诉用户去新 Agent 打开项目并说"请阅读 HANDOVER.md 和项目说明书，完成入职验证"。我进入只读顾问期。

## 🆕 新 agent 工作流（接收方）

### 第 3 步：环境确认
- 找到并阅读 HANDOVER.md（确认状态为 PENDING）
- 找到并阅读项目说明书（AGENTS.md 等）
- 确认 .env / 密钥 / 本地数据库等配置已就位
- 确认远程仓库访问正常

### 第 4 步：验证与生命周期闭环

**阶段 A：只读入职**
全程只读、不修改任何文件：阅读 HANDOVER.md 和项目说明书 → 浏览目录结构 → 运行安装/测试/构建 → 汇报现状及与交接文档不符之处。等待用户确认。

**阶段 B：受控小任务与人类审核**
请用户指定小改动（修小 bug、补测试、加字段）。严格按约定动手，不碰范围外。**完成后生成 `git diff` 供人类审核，严防篡改测试断言作弊。**

**阶段 C：交接闭环与归档（关键！）**
人类审核通过后，新 agent 必须完成收尾闭环：
1. 将 `HANDOVER.md` 中稳定下来的技术事实回填沉淀到项目说明书（`AGENTS.md` 等）。
2. **将 `HANDOVER.md` 归档移走**：先确保归档目录存在（`mkdir -p docs/handover`），再移至 `docs/handover/HANDOVER_YYYYMMDD_<交出方>_to_<接收方>.md`（或将头部状态更新为 `COMPLETED`）。
3. 提交本次入职验证及归档修改到 git。

完成后告诉用户："入职验证与归档闭环完成。可以开始正式接受开发任务了。请将本 AGENTS.md 替换为常规项目说明书，恢复日常开发。"

## 红线
1. 新旧 agent 不要同时改文件
2. 别假设新 agent "应该知道"任何事
3. 交接文档中禁止明文密钥、Token、私网 IP 或真实业务测试数据
4. 没有带时间戳的回滚 tag 不要开始交接
5. 不要跳过验证与人类 Diff 审计步骤
6. **交接完成后必须归档或标记 HANDOVER.md**

## 回滚与应急
- 回退：`git checkout <handover-before-tag名称>`
- 保留旧 agent 1-2 周只读顾问期
- 发现遗漏：回旧 agent 写成文档再带回来，不要凭记忆硬补
